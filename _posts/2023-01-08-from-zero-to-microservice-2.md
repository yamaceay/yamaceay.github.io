<h4>How to Dockerize Your App &amp; Deploy using Kubernetes?</h4><p>Previous articles:</p><p><a href="https://yamaceay.medium.com/microservices-101-d6395c153890">Microservices 101</a></p><p><a href="https://yamaceay.medium.com/from-zero-to-microservice-1-8adbf7d12473">From Zero To Microservice [1]</a></p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*dXYVkl1wDEThxncwQpFBUA.jpeg" /><figcaption>Fig 1: How deployment figuratively looks like, Source: <a href="https://entwickler.de/programmierung/deployment-automatisch-praktisch-gut-001">https://entwickler.de/programmierung/deployment-automatisch-praktisch-gut-001</a></figcaption></figure><h4>Step 0: Get a Project</h4><p>I created a GitHub repository <em>person_grpc</em> [1]: a Go package, which serves as a personal database, dealing with get / set person commands. The communication between server and client is achieved using gRPC (built on top of TCP).</p><h4>Step 1: Go Project =&gt; Docker Image</h4><p>Requirements: <a href="https://docs.docker.com/desktop/install/mac-install/">Docker</a> + <a href="https://www.docker.com/products/docker-desktop/">Docker Desktop</a> are installed on your computer.</p><p><em>Docker image</em> ( = a program) is basically a schema of <em>Docker containers</em> ( = running processes).</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*CwqgJKDweKgfkjDzbH_KIw.jpeg" /><figcaption>Fig 2: Docker Images and Containers, Source: <a href="https://jfrog.com/knowledge-base/a-beginners-guide-to-understanding-and-building-docker-images/">https://jfrog.com/knowledge-base/a-beginners-guide-to-understanding-and-building-docker-images/</a></figcaption></figure><h4>Building a Docker Image</h4><p>Dockerfile is used for building a from a <em>specific implementation</em>. It specifies the following commands as below.</p><p><code>FROM &lt;image-version&gt; [AS &lt;image-alias&gt;]</code>:</p><ul><li>A <em>parent image</em> is <em>fetched</em> and used in the following commands.</li><li>Until next <code>FROM</code> command, the target image remains unchanged.</li></ul><p><code>WORKDIR &lt;path&gt;</code>:</p><ul><li>The current <em>working directory </em>is changed to <code>&lt;path&gt;</code> inside a container.</li><li>It is linked to the nearest previous <code>FROM</code> command.</li></ul><p><code>COPY [--from=&lt;image-alias&gt;|&lt;image-version&gt;] &lt;src-path&gt; &lt;dest-path&gt;</code>:</p><ul><li>It moves the <em>specified file / folder</em> from source directory / image to the <em>destination path</em>.</li><li>Same as <code>WORKDIR</code>, it is also linked to the previous <code>FROM</code> command.</li><li>If an <em>image alias</em> is given <code>--from=&lt;image-alias&gt;</code>, source path is looked up in given image.</li><li>If the source image is only used once, <em>image version</em> can be used instead.</li></ul><p><code>RUN &lt;build-cmd&gt;</code>: When building Docker image, this command is executed inside<em> target image</em>.</p><p><code>ENTRYPOINT | CMD [&quot;&lt;run-cmd-arg1&gt;&quot;, &quot;&lt;run-cmd-arg2&gt;&quot;, ...&quot;]</code>: When starting the Docker container, these commands are executed.</p><p>An example of expected behaviour: A program <code>./main</code> inside target image requires exactly one positional argument <code>$port</code>:</p><p><code>ENTRYPOINT [&quot;/bin/sh&quot;, &quot;-c&quot;, &quot;./main&quot;]; CMD [&quot;8080&quot;]</code></p><ul><li><code>docker run -it &lt;image&gt;</code> =&gt; <code>$port</code> is set to 8080</li><li><code>docker run -it &lt;image&gt; 6379</code> =&gt; <code>$port</code> is set to 6379</li></ul><p><code>ENTRYPOINT [&quot;/bin/sh&quot;, &quot;-c&quot;]; CMD [&quot;./main&quot;, &quot;8080&quot;]</code></p><ul><li><code>docker run -it &lt;image&gt;</code> =&gt; <code>$port</code> is set to 8080, <code>./main</code> is running</li><li><code>docker run -it &lt;image&gt; ./main</code> =&gt; <code>./main</code> fails to start because no positional argument is given</li><li><code>docker run -it &lt;image&gt; ./main 6379</code>=&gt; <code>$port</code> is set to 6379, <code>./main</code> is running</li></ul><p>An example of <code>Dockerfile</code> (with build and run stages):</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*PyhskCAB2PzHoXDnc3bqQA.png" /><figcaption>Fig 3: Dockerfile (with build and run stages)</figcaption></figure><p>A Docker image can be built using <code>docker build . -t &lt;image-name&gt;</code>. If you have multiple images in the same project, you can define more than one Dockerfiles and specify the Dockerfile using the flag <code>-f &lt;custom-path-to-Dockerfile&gt;</code>.</p><h4>Running &amp; Debugging a Docker Container</h4><p>For running the Docker container in the background and exposing it in the local host, enter: <code>docker run [--rm] -d -p [&lt;host&gt;:]&lt;port&gt;:&lt;intern-port&gt; &lt;image-name&gt;:latest</code>. This does the following:</p><ul><li><code>--rm</code>: <em>Remove</em> the container if stopped</li><li><code>-d</code>: <em>Detach</em> the container process from the terminal and return the container id instead</li><li><code>-p [&lt;host&gt;:]&lt;port&gt;:&lt;intern-port&gt;</code>: <em>Expose</em> the application running actually on <code>&lt;intern-port&gt;</code> to <code>&lt;port&gt;</code> at current host (<code>&lt;host&gt;</code> if specified, otherwise any host)</li></ul><p><code>docker inspect &lt;container-id&gt;</code> prints <em>all details</em> of a container:</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*6AAGUdMW0d_gmmeQR6s0Cg.png" /><figcaption>Fig 4: Inspecting a container</figcaption></figure><ul><li>Running command is <code>./server -f config.yaml</code> (see <code>&quot;Path&quot;</code> and <code>&quot;Args&quot;</code>).</li><li><code>&quot;50051/tcp&quot;</code> is successfully exposed in address: <code>localhost:50051</code> (see <code>&quot;PortBindings&quot;</code>).</li></ul><p><code>docker run -it &lt;image-name&gt; /bin/sh</code> opens the shell terminal inside a Docker container:</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*regof_J-U7OYKpiOaXyemg.png" /><figcaption>Fig 5: Showing inside Docker container</figcaption></figure><ul><li><code>config.yaml</code> is copied successfully — so hosts and ports are successfully configured at each build.</li><li><code>./server</code> is there too — running <code>./server -f config.yaml</code> inside terminal has the <em>same effect</em> as running the container.</li></ul><p><code>docker ps</code> shows all the <em>active</em> Docker containers. If used with <code>-a</code> flag, it shows all containers.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*UmooAU5tNikW053hNlrdqQ.png" /><figcaption>Fig 6: Showing all active Docker containers</figcaption></figure><ul><li>Docker container is <em>accessible on port</em> <code>50051</code> for TCP connections (and universal host <code>0.0.0.0</code>)</li></ul><p>Let’s run the client:</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*P3bm9Ndfh8cC-bEWT0uCxw.png" /><figcaption>Fig 7: Running the client</figcaption></figure><p><code>docker logs &lt;container-id&gt;</code> prints all the messages logged by server. If used with <code>-f</code> flag, it <em>monitors</em> the logs until termination.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*RbFeAGcYQSuSofpb3k_7ig.png" /><figcaption>Fig 8: Logging inside Docker container</figcaption></figure><p>Now we’ll see how to <em>deploy</em> it on a local Kubernetes cluster.</p><h4>Step 2: Docker Image =&gt; Kubernetes Deployment</h4><p>Requirements: <a href="https://kubernetes.io/de/docs/tasks/tools/install-minikube/">Minikube</a> and <a href="https://helm.sh/docs/intro/install/">Helm</a> installed on your computer.</p><p>Helm is an essential <em>package manager</em> for Kubernetes, which <em>automates</em> the Kubernetes applications lifecycles [4] and includes many advanced features as listed in [5]. It is however out of scope of this article.</p><p>First, let’s start a Minikube cluster using <code>minikube start</code>:</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*Do13hOBXSoRzOTOyEs9_lA.png" /><figcaption>Fig 9: Starting a local cluster</figcaption></figure><h4>Creating a Kubernetes Deployment</h4><p>Since the local cluster doesn’t know about the Docker image, let’s <em>load the image</em> into the cluster <code>minikube image load &lt;image&gt;</code> (this may take a few minutes, depending on how big your image is).</p><p>Docker image is downloaded, but nothing is deployed yet. Kubernetes-equivalent for a Docker image is called <em>deployment</em>.</p><p>To create a new deployment, we create a new <code>&lt;image&gt;.yaml</code> inside a new directory called <code>deploy</code> with the following content:</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*HfpkNGrIeD5xTiU7SdqOsw.png" /><figcaption>Fig 10: Deployment configuration</figcaption></figure><p>I copied-pasted it from the <a href="https://kubernetes.io/docs/concepts/workloads/controllers/deployment/">docs</a>. Differences:</p><ul><li><code>imagePullPolicy: Never</code>: We already pulled the image from Docker manually. Setting it to <em>Never</em> guarantees that Kubelet won’t attempt to download it automatically.</li><li><code>replicas: 1</code>: We want to keep it very simple. Only one <em>pod</em> is needed (also the Kubernetes-equivalent to Docker containers).</li></ul><p>Then we create the deployment using <code>kubectl apply -f deploy/&lt;image&gt;.yaml</code> inside the cluster.</p><p>Enter <code>kubectl get deployments</code> to see that there is one deployment:</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*XCVXL6pnE3KAfuN7XS528A.png" /><figcaption>Fig 11: Deployments</figcaption></figure><p>and similarly <code>kubectl get pods</code> to see all the pods:</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*BiO_zbFTVS3DuQRCJxVeMg.png" /><figcaption>Fig 12: Pods</figcaption></figure><p>Or if you have many pods from other deployments, you can filter the pods using labels. For example: <code>-l app=person-server</code> would get the <code>person-server</code> pod.</p><p>If we delete a pod using <code>kubectl delete pod &lt;pod-name&gt;</code>, a new pod is created automatically:</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*9jsh-2-XAEws4qR0a1PFDQ.png" /><figcaption>Fig 13: New pod is created</figcaption></figure><p>A few analogies:</p><ul><li><code>docker inspect &lt;container-id&gt;</code> v. <code>kubectl describe pod &lt;pod-name&gt;</code></li><li><code>docker build ...</code> v. <code>kubectl apply ...</code></li><li><code>docker run ...</code> is handled automatically by Kubernetes after <code>apply</code> (that’s why it is called deployment)</li><li><code>docker run -it &lt;container-id&gt; &lt;command&gt;</code> v. <code>kubectl exec -it &lt;pod-name&gt; -- &lt;command&gt;</code></li><li><code>docker logs &lt;container-id&gt; [-f]</code> v. <code>kubectl logs &lt;pod-name&gt; [-f]</code></li></ul><h4>Exposing the Application</h4><p>Now the whole application is running in the local cluster, so it can communicate with other pods inside the local cluster, but not with the external world yet. Exposing the application can be done in numerous ways:</p><p><strong>Option #1: Exposing a Pod</strong></p><p><code>kubectl port-forward &lt;pod-name&gt; -p &lt;port&gt;:&lt;intern-port&gt;</code></p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*ba_afL3QZXpKnfxwKgteXw.png" /><figcaption>Fig 14: Kubernetes Pod exposed locally</figcaption></figure><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*80m_Z2DCCbpr-2yIe-cw4g.png" /><figcaption>Fig 15: Client can connect</figcaption></figure><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*Bj44-RDGzl_nuKtY9tkCuQ.png" /><figcaption>Fig 16: Kubernetes Pod handling the requests</figcaption></figure><p><strong>Option #2: Exposing a (NodePort) Service</strong></p><p>Let’s define a new service in Kubernetes in <code>deploy/&lt;image&gt;-service.yaml</code>:</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*_eNG7Qh69BPfVUQE1cPIlw.png" /><figcaption>Fig 17: Service configuration</figcaption></figure><p>The template can be downloaded from the <a href="https://kubernetes.io/docs/concepts/services-networking/service/">docs</a> as well. Differences:</p><ul><li>The service is a <em>NodePort</em>, which serves as the external entry point for incoming requests for your app [7].</li><li>The service has the same app name as the deployment <code>person-server</code>, so they belong together.</li><li>The <em>actual deployment</em> runs on port 50051. The service, which is <em>actually running</em> on port 32222 in local cluster, is <em>accessible for TCP connections</em> on port 8080.</li></ul><p>If we run <code>kubectl port-forward svc/&lt;service&gt; -p &lt;port&gt;:&lt;port&gt;</code>, we would get the same results as before.</p><p>If the application is able to handle HTTP requests, it can be also exposed using: <code>minikube service &lt;service&gt; --url</code>.</p><p><strong>Option #3: Exposing an Ingress</strong></p><p>Exposing a NodePort may not be a solution itself, but can be seen as an <em>intermediary step</em> to create an Ingress: a <em>backend</em> for your services, which makes your services <em>accessible</em> from outside of the local cluster using HTTP requests. Using an Ingress, the whole application would look like:</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*vGOo8pCPrMt1RgSbPUrUIA.png" /><figcaption>Fig 18: Ingress, Source: <a href="https://banzaicloud.com/blog/k8s-ingress/">https://banzaicloud.com/blog/k8s-ingress/</a></figcaption></figure><p>I don’t want to go into detail, because Ingress can only <em>route</em> HTTP requests (and this does not fit into our application). Hypothetically, if our application were communicating using HTTP requests, Ingress for our application could be defined as below:</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*l4YotsdObobvxixdN0WaTg.png" /><figcaption>Fig 19: Ingress configuration</figcaption></figure><h4>Final Thoughts</h4><p>This concludes our series From Zero to Microservice. Now we have built a very simple gRPC server, which is then Dockerized and deployed in a local Kubernetes cluster.</p><p>This article is not based on any documentation: I wrote based on my practical experiences and what I have learned by trial-and-error in my job.
