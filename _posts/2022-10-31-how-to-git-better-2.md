<p>… so you can be a more decent human being in the next projects :-)</p><p>Previous chapter:</p><p><a href="https://yamaceay.medium.com/how-to-git-better-1-ef996cb86a23">How To Git Better— 1</a></p><p>A <em>remote</em> is an online repository which can be downloaded as a local repository and updated thereafter.</p><h4>Managing Remotes &amp; Remote Branches</h4><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*IVxUFPopbIuJxBNLEUNrcw.png" /></figure><p>Git works with remote aliases, not with URL addresses.</p><p>This is how you store the URL addresses of remote repositories in aliases:</p><p><code>git remote add &lt;remote&gt; &lt;URL&gt;</code>: Save the URL of remote repository as a variable.</p><p><code>git remote remove &lt;remote&gt;</code>: Remove the remote from the local repository.</p><p>There are two types of branches in local repositories:</p><p><code>&lt;branch&gt;</code> is a local branch which you work with locally, and</p><p><code>&lt;remote&gt;/&lt;branch&gt;</code> is the copy of the branch existing on a remote repository</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*p3x8pRQ09vNn3gMjyqkUhw.png" /></figure><p>And here are some interesting points worth mentioning:</p><ul><li>There can be multiple remote branches for any local branch.</li><li>Remote1 doesn’t have to contain every branch that remote2 contains.</li><li>Remote2 doesn’t have to contain every branch that local contains.</li></ul><h4>Splitting Processes</h4><p>Branches can be visualized as workflows of developers working in an isolated manner for the development of a feature etc.</p><p>There is only one <code>main</code> branch, which can be seen as the main product that the whole team is working on separately.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*XiJfxZHYxKIaUhBAp20fVw.png" /></figure><p>This is how you create and switch your workflow:</p><p><code>git branch -v</code> : Show the list of branches and their latest commits</p><p><code>git branch &lt;branch&gt;</code>: Create a new branch</p><p><code>git checkout &lt;branch&gt;</code> : Switch to the branch</p><h4>Posting and Receiving an Update</h4><p>The changes can be exchanged mutually with the remote repositories whose URLs are known by local repository.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*01S-onVBrHzNkbyor5c3Tg.png" /></figure><p><code>git push &lt;remote&gt; &lt;branch&gt;</code> : Share the commits in the target branch of remote repository, similar to uploading an app.</p><p><code>git fetch &lt;remote&gt;</code> : Get the latest versions of remote branches from a remote repository, similar to downloading an app.</p><p><code>git pull &lt;remote&gt;</code>: Merge the changes fetched from remote repository into the local branches, similar to downloading &amp; installing an app.</p><h4>Joining Processes</h4><p>Since we know how to create branches, now it’s time to explore how to join the branches together.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*ZSlxMLu5hbIjiePGO23UBA.png" /></figure><p>There are two ways to accept an incoming change:</p><p><code>git merge &lt;branch&gt;</code> : Accept the changes made in target branch to the current branch.</p><p><code>git rebase &lt;branch&gt;</code> : Accept the new changes of the target branch and add the changes made in current branch on top of them.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*Q7mjbWTZ8WrNr_7uHZVswA.png" /></figure><p><em>Note</em>: You can use <code>git rebase --onto &lt;new-base-commit&gt; &lt;old-base-commit&gt; &lt;moved-commit&gt;</code> for rebasing on the commit-level.</p><p>An example:</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*HvmsFUmVXZl8bLgdpnLyAQ.png" /></figure><h4>Dealing With Conflicts</h4><p>In the following, I try to answer the WH-Questions of merge conflicts.</p><p><em>How does it look like?</em></p><p>For example, let’s look at the conflict in a file named <code>constants.go</code>, which originally doesn’t include <code>var pi</code>:</p><pre><code>var e = 2.73</code></pre><pre><code>&lt;&lt;&lt;&lt;&lt;&lt;&lt; HEAD
var pi = 3.14
=======
var pi = 3.1415
&gt;&gt;&gt;&gt;&gt;&gt;&gt; branch1</code></pre><p>The current branch <code>HEAD</code> suggests to use <code>3.14</code> , and the other branch <code>branch1</code> vice versa.</p><p><em>When does it happen?</em></p><ul><li>Merge</li><li>Rebase</li><li>Pull (because Pull = Fetch + Merge)</li></ul><p><em>Why does it happen?</em></p><ul><li>Because your branch and other branch try to modify the same file.</li></ul><p><em>Is it a bad luck to have conflicts?</em></p><ul><li>No, it is not a bad thing, it just points the area of conflicts and the main branch has to decide on what is going to be included.</li><li>Unless it happens more than necessary, it should be no problem.</li></ul><p><em>How to detect it?</em></p><ul><li>You can use the command <code>git status</code> to check:</li></ul><pre><code>&gt; # On branch branch1
&gt; # You have unmerged paths.
&gt; #   (fix conflicts and run &quot;git commit&quot;)
&gt; #
&gt; # Unmerged paths:
&gt; #   (use &quot;git add ...&quot; to mark resolution)
&gt; #
&gt; # both modified:      constants.go
&gt; #
&gt; no changes added to commit (use &quot;git add&quot; and/or &quot;git commit -a&quot;)</code></pre><p><em>How to resolve it?</em></p><ul><li>Accepting incoming change: Use <code>branch1</code>‘s definition of <code>pi</code>: <code>3.1415</code> and delete everything in conflict part except for <code>var pi = 3.1415</code></li><li>Accepting current change: Use <code>HEAD</code>‘s definition of <code>pi</code>: <code>3.14</code> and delete everything in conflict part except for <code>var pi = 3.14</code></li></ul><p>In VSCode: If you are sure that you only want to use the <code>HEAD</code>&#x27;s changes, you can use<code>Accept All Current Changes</code> and similarly if you only include the changes of <code>branch1</code>, it would be <code>Accept All Incoming Changes</code>.</p><p>Then use simply <code>git add</code> to stage your changes and <code>git commit</code> to apply your changes.</p><p>If we created a whole new <a
