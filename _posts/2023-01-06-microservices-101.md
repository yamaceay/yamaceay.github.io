<h4>Impress anyone with these buzzwords: …</h4><h4>What is a Microservice?</h4><p>Before answering that, I want to answer what is NOT:</p><p><em>Monolith Server</em>: The most <strong>traditional</strong> approach to create an application, e.g. an application contains a client-side, a server-side and a database, and relies on a single server.</p><p><em>Service Oriented Architecture (SOA)</em>: The application consists of cohesive <strong>business processes</strong>, communicating through Enterprise Service Bus (ESB).</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*sljw1P79Ej22xnVs3oyMgg.jpeg" /><figcaption>Fig 1: Lego-like development using Microservices</figcaption></figure><p>According to Martin Fowler [1], microservices are “small services, each running in its own process and communicating with lightweight mechanisms, often an HTTP resource API.”</p><blockquote>These services are built around business capabilities and independently deployable by fully automated deployment machinery. There is a bare minimum of centralized management of these services, which may be written in different programming languages and use different data storage technologies.</blockquote><p>And, there are also many <strong>common features</strong> shared across microservices, such as:</p><p><em>Componentization via Services</em>: Services are as decoupled and as cohesive as possible.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*U6vfdpnblRIoRVN-AgJ29g.jpeg" /><figcaption>Fig 2: An application separated in services</figcaption></figure><p>2 types of components:</p><ul><li><em>Libraries</em>: components that are linked into a program and called using <strong>in-memory</strong> function calls.</li><li><em>Services</em>: <strong>out-of-process</strong> components who communicate with a mechanism such as a web service request, or remote procedure call (RPC).</li></ul><p>A RPC creates the illusion of calling a library function when in fact a service function is called (more on RPC in the next sections).</p><p><em>Smart Endpoints, Dumb Pipes</em>: An endpoint contains the whole core <strong>functionality</strong>, whereas a pipe acts only as a message <strong>router</strong>.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*LZGlrWOXeqtEiWFrQy1p3w.png" /><figcaption>Fig 3: Similarly, Smart Endpoints &amp; Dumb Pipes in Internet Layers</figcaption></figure><p><em>Infrastructure Automation</em>: The whole infrastructure details of a program can be configured e.g. by using YAML files as follows:</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*5JOIVDuIXU4i7qNsVF58Wg.png" /><figcaption>Fig 4: Infrastructure as Code, Example of Configuring a Kubernetes Deployment</figcaption></figure><p>There are too many definitions online and no clear way of putting them all together, partly because it is more of a <strong>basic concept</strong> than a program.</p><p>I find it more intuitive to think of them as the <strong>pure abstraction</strong> of a program:</p><ul><li>I don’t care about the underlying <strong>implementation</strong> (e.g. Go, Kotlin, Node.js or Python),</li><li>I just need to know its <strong>API</strong> (what this service does).</li></ul><h4>Relaxing Communication Between Services</h4><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*SwgSxDgayE0h4SPQyGuclw.png" /><figcaption>Fig 5: Loose Coupling vs. Tight Coupling</figcaption></figure><p>Apart from services which have to communicate in <strong>real-time</strong>, <strong>tight coupling</strong> — generally— stresses the whole application.</p><p>There are 2 very important<strong> decoupling methods</strong> used for separating the tightly coupled services:</p><ul><li><em>Time Decoupling</em>: Services can communicate at different time points</li><li><em>Space Decoupling</em>: Services can communicate from different locations</li></ul><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*pUTES6UWBzzrh24HTz38iw.png" /><figcaption>Fig 6: XML as an example for universal data exchange language</figcaption></figure><p>Similarly, <strong>data format dependency</strong> is another issue, which can be solved using:</p><ul><li><em>Marshaling, Serialization</em>: mapping any type of data to a <strong>common</strong> universal representation, and</li><li><em>Unmarshaling, De-serialization</em>: reading a common representation of data and <strong>casting</strong> it (back) into a language-specific data structure.</li></ul><p>The most important <strong>serialization notations</strong> include:</p><ul><li><em>JavaScript Object Notation (JSON)</em>: <strong>Human-readable</strong> data representation</li><li><em>YAML Ain’t Markup Language (YAML)</em>: Similar to JSON without parentheses</li><li><em>eXtensible Markup Language (XML)</em>: HTML-like data representation</li><li><em>Protocol Buffers (Protobuf)</em>: A type of <strong>binary</strong> serialization</li></ul><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*HFiYiBlJ11FB7xdZ8qRh4Q.png" /><figcaption>Fig 7: Data exchange using REST vs. GraphQL vs. gRPC</figcaption></figure><p>By way of serialization, e.g. typical GET/POST requests can be done using <strong>any type of data</strong>. There are a few frameworks/languages [2] used in communication:</p><ul><li><em>REST</em>: an API format which uses HTTP methods like <code>GET</code>, <code>POST</code>, <code>PUT</code>, and <code>DELETE</code> to access and manipulate data within uniform resource identifiers (URIs), prefers JSON or XML</li><li><em>GraphQL</em>: a data query language that uniquely allows clients to request any specific data that they need, prefers JSON</li><li><em>gRPC</em>: a remote procedure call (RPC) framework, uses Protocol Buffers</li></ul><h4>Tech Stack for Microservices</h4><p>In the following, I’ll explain the 2 most infamous buzzwords of software era: <strong>Docker</strong> and <strong>Kubernetes</strong>.</p><h4>What is Docker?</h4><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*L8l6zrNBNySPu19jNNS6LA.png" /><figcaption>Fig 8: Docker</figcaption></figure><p><em>Motto</em>: Build, Ship, Run</p><p>The following example illustrates how different the run commands would look like, in case of different OS and/or different programming languages/frameworks:</p><ul><li>A Go package is executed using <code>go run . &lt;args&gt;</code></li><li>A Python program is executed using <code>python main.go &lt;args&gt;</code> in Windows, but <code>python3 main.go &lt;args&gt;</code> is used in Mac instead</li><li>A Java class is built and executed using <code>javac Main.java &amp;&amp; java Main &lt;args&gt;</code></li><li>A Node.js program is executed using <code>node main.js &lt;args&gt;</code></li></ul><p>It’s very exhausting to remember every little detail where to use what run/build command. I find the analogies from [3] somewhat very relatable:</p><blockquote>For many years now, enterprise software has typically been deployed either on “bare metal” (i.e. installed on an operating system that has complete control over the underlying hardware) or in a virtual machine (i.e. installed on an operating system that shares the underlying hardware with other “guest” operating systems).</blockquote><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*mWBQzk-uozo7Cz7aw2wf0A.png" /><figcaption>Fig 9: Virtual Machines vs. Containers</figcaption></figure><p>In comparison, a Docker container is executed using <code>docker run image</code> on any OS, and it may contain any program from any programming language.</p><p>Unanimously, Docker is a suite of tools for developers to build, share, run and orchestrate <strong>containerized apps</strong> [4]. A Docker container isolates a single application and its dependencies both from the underlying operating system and from other containers.</p><h4>What is Kubernetes?</h4><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*pzOL3V84nomqSe5LLdnbAA.png" /><figcaption>Fig 10: Kubernetes (Left side: Actual Services, Right side: Proxy)</figcaption></figure><p><em>Motto</em>: Servers come and go, services stay forever.</p><ul><li>Running a large-scale application on too few server instances is not a good idea, especially if the servers are expected to <strong>crash/fail periodically</strong>.</li><li>Running it on too many servers equals however unnecessarily <strong>high costs</strong> and waste of resources.</li></ul><p>That’s why auto-scaling is <strong>essential</strong> in modern applications. This is one of the main reasons Kubernetes is used <strong>worldwide</strong>. As defined in [5]:</p><blockquote>Kubernetes is open-source orchestration software that provides an API to control how and where those containers will run. It allows you to run your Docker containers and workloads and helps you to tackle some of the operating complexities when moving to scale multiple containers, deployed across multiple servers.</blockquote><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*vNsy8d8hx8kCPbTX8QmgtA.png" /><figcaption>Fig 11: Example of Autoscaling</figcaption></figure><p>Kubernetes provides an easy way to scale your application, compared to virtual machines. It keeps code operational and speeds up the delivery process. […] allows automating a lot of resource management and provisioning tasks.</p><p>It also “helps with networking, load-balancing, security and scaling across all Kubernetes nodes which runs your containers.”, as stated in [6].</p><h4>So: Docker + Kubernetes + …?</h4><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*HmyfffyLrrBJ6dF7m2mKfA.jpeg" /><figcaption>Fig 12: Docker + Kubernetes</figcaption></figure><ul><li><strong>Docker</strong> underlies the boring implementation details and runs the program <strong>on every machine</strong>.</li><li><strong>Kubernetes</strong> optimizes the performance of the whole application and makes it <strong>reliable</strong> for the end user.</li></ul><p>Okay, so what happens thereafter?</p><p>You can fill in the blanks with <strong>any tech stack you choose</strong> in your next project, it doesn’t matter. It is a very powerful tech stack, which enables you to make your program more flexible.</p><p>I’ll proceed this article with a brand new upcoming article series on how to create a simple microservice
