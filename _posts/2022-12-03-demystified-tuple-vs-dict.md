<h4>The real distinction between tuples and dicts, and how it relates to Dependency Injection, Joining of SQL Tables and more…</h4><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*xDxA89_NTuzbm9Ke5B11-Q.png" /><figcaption>Fig 1: Tuple vs. Dict</figcaption></figure><p>Technically, <em>tuples</em> and <em>dicts</em> are equivalent in terms of content: Tuples select the feature by positional <em>index</em>, while dicts select by a unique identifier called <em>key</em>.</p><p><em>Note</em>: In this article, I prefer to use <em>tuple</em> and <em>dict</em> as in Python, since there is no universal name for both. If you come from a Go background, it’s <em>struct</em> and <em>map </em>respectively.</p><h4>Table of Contents</h4><p><em>1.1: </em>Information is Stored as Tuple by Default</p><p><em>1.2: </em>Tuples Can Be Compared Among Themselves</p><p><em>1.3: </em>Tuples Cannot Interact With Other Types of Tuples</p><p><em>2.1: </em>Dependency Injection: What, How, Why?</p><p><em>2.2: </em>Mocking Using Dependency Injection</p><p><em>2.3: </em>How Dependency Injection Relates to Tuples vs. Dicts</p><p><em>3: </em>Step-by-Step Construction of Dicts in Maths: Multiset, Ordered Set, Abstract Tuple, Dict</p><p><em>4.1: </em>Dependency Injection on Person-Animal Comparison</p><p><em>4.2: </em>How Merging Two Tuples Would Work Using Dicts</p><p><em>4.3: </em>How Tuple vs. Dict Relationship Is Related to Joining Datasets</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*GUkFK5KIjJ8JQe9XDSXhOg.png" /><figcaption>Fig 2: Visualization of Information</figcaption></figure><h4>Information is Stored as Tuple by Default</h4><p>Unlike dicts, the features of tuples are <em>strictly</em> defined, and also their <em>domains</em> are known, which is why tuples are much <em>safer</em> to use.</p><p>Before <em>looking</em> <em>up</em> a feature from a tuple, you need to first make sure that the tuple contains this feature and the position of feature is known.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*IG6mX6FHYTbtzQ_PRQyC4g.png" /><figcaption>Fig 3: Same Type of Tuples</figcaption></figure><h4>Tuples Can Be Compared Among Themselves</h4><p>With this in mind, tuples of same kind can be<em> compared</em> and sorted based on their features. For example:</p><ul><li>Let’s define a person <em>signature</em> as follows: <strong>P_i = (a_i, w_i, h_i)</strong> where <strong>a_i </strong>is “age”, <strong>w_i</strong> is “weight” and <strong>h_i</strong> is “height”.</li><li><strong>f</strong> is a function which stands for “isYounger”: <strong>f(P_1, P_2) = a_1 &lt; a_2.</strong></li><li><strong>g</strong> is a function which stands for ”isTallerOrHeavier”: <strong>g(P_1, P_2) = h_1 &gt; h_2 ∨ w_1 &gt; w_2.</strong></li><li>Two instances are given: <strong>P_1 = (18, 80, 1.79) </strong>and <strong>P_2 = (21, 84, 1.85)</strong>. <strong>f(P_1, P_2)</strong> outputs “YES” and <strong>g(P_1, P_2) </strong>outputs “NO”.</li><li>Selecting a comparison function of our wish as the ranking criteria among person tuples, we can sort persons.</li></ul><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*7G48JM3wdc9yeP51VWMLUQ.png" /><figcaption>Fig 4: Different Types of Tuples</figcaption></figure><h4>Tuples Cannot Interact With Other Types of Tuples</h4><p>But what if we wanted to compare animals too?</p><ul><li>Let’s say animals have a different <em>signature</em>: <strong>A_j = (z_j, h_j, w_j, a_j)</strong> where <strong>z_j</strong> is an additional feature standing for the “genus of an animal”.</li><li>We would have to define P2P (“person-to-person”), P2A, A2P and A2A comparing functions.</li><li>For example: <strong>l(P_1 = (a_1, w_1, h_1), A_2 = (z_2, h_2, w_2, a_2)) = w_1 &lt; w_2</strong> for compares the weights of a person and an animal.</li><li>Even without an additional feature <strong>z_i</strong>, the comparison function would be a mess, since the order of features play a key role.</li></ul><p>So it’s pretty clear that tuples are not capable of <em>interacting</em> with other types of tuples.</p><p>As we’ll later see, this problem can be solved using clever tricks, such as casting the tuples to dicts and performing the comparison. But first, we have to gain an understanding of a very powerful technique called <em>dependency injection</em>.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*z5U7aJA6C_u3dUsckcosWQ.jpeg" /><figcaption>Fig 5: Dependency Injection</figcaption></figure><h4>Dependency Injection: What, How, Why?</h4><p>Given:</p><ul><li><code>class Person { int age; int weight; int height; }</code></li><li><code>class Animal { string genus; int height; int weight; int age; }</code></li><li><code>bool compare (Person either, Person other){ return either.age &lt; other.age; }</code> which defines the pairwise comparison criteria of people.</li></ul><p>Task:</p><ul><li>Extend the code so that we can compare humans with animals too.</li></ul><p>Solution:</p><ul><li>Extract a common <em>comparable interface</em> for persons and animals: <code>interface AgeComparable { int age(); }</code></li><li>Implement <code>int age()</code> in people class <code>class Person implements AgeComparable {int age; int weight; int height; int age() { return this.age; }; }</code> (and the same applies for animals)</li><li>Extend the comparing function by interface: <code>bool compare (AgeComparable either, AgeComparable other){ return either.age() &lt; other.age(); }</code>, so that comparing function only specifies <em>what</em> feature it needs, without having to know <em>how</em> to get the feature.</li></ul><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*NOf-iPtQo9U2Efp52OhfQg.jpeg" /><figcaption>Fig 6: Mocking Using Dependency Injection</figcaption></figure><h4>Mocking Using Dependency Injection</h4><p>Dependency Injection comes in very handy in situations where testing an operation can affect the <em>whole</em> system in an undesirable manner.</p><p>Mocking allows you to <em>isolate</em> the operation from the real environment and perform tests in <em>sandboxes</em>, for example:</p><ul><li>You want to test an operation <code>int post_content(string content, Server server) { return server.post(&quot;localhost:8080&quot;, content); }</code> which internally makes a real HTTP request using <code>class Server { int post(string content) { // real http request }; }</code>.</li><li>For this, you extract an <code>interface ServerInterface { int post(string content);</code> and adapt <code>class Server implements ServerInterface { ... }</code>, then create a <code>class MockServer implements ServerInterface { int post(string content) { return 0; }; }</code> with a “harmless” post operation and finally update the function parameter <code>int post_content (string content, ServerInterface server) { ... }</code>.</li></ul><h4>How Dependency Injection Relates to Tuples vs. Dicts</h4><p>In the most basic words, dicts are <em>dependency-injected</em> tuples, which serve as a <em>common</em> interface of features across <em>different</em> tuples and used mainly in case the features of tuples are <em>not necessarily known</em>.</p><p>Formally, it can be seen as the <em>key-value pairs</em> (k, v) inside a set where each key is mapped to a value <em>uniquely</em>.</p><p>For the simplicity, I borrow the same notations from my previous article “Sets &amp; Tuples”, which deals with the two most basic data structures used in maths. I recommend you to take a look if you haven’t seen.</p><p><a href="https://yamaceay.medium.com/sets-tuples-ef4a975c80c7">Sets &amp; Tuples</a></p><h4>Step-by-Step Construction of Dicts in Maths</h4><p><strong><em>Multiset</em></strong></p><p>The key difference from sets is that each element can occur <em>multiple</em> times in multisets. It is notated as <strong>v_1, v_2, …</strong> instead of<strong> {v_1, v_2, …}</strong></p><p><strong><em>Ordered Set</em></strong></p><p>Let’s define a tuple <strong>(i, v_i)</strong> for each<strong> i ∈ ℕ </strong>whereas <strong>v_i ∈ {v_1, v_2, …} </strong>inside a set called <strong>V_ℕ = {(i, v_i) | i ∈ ℕ, v_i ∈ {v_1, v_2, …}}.</strong></p><p>We could name <strong>V_ℕ </strong>as an <em>ordered</em> <em>set</em>, where each<strong> i</strong> acts as a <em>unique</em> identifier for each <strong>v_i</strong>.</p><p>However, it cannot be a building block of dict, because the values in <strong>V_ℕ</strong> are <em>restricted </em>unnecessarily so that no value <strong>v_i ∈ {v_1, v_2, …}</strong> can occur multiple times.</p><p><strong><em>Abstract Tuple</em></strong></p><p>Switching value domains to multiset <strong>v_i ∈ v_1, v_2, …</strong> instead, now we can guarantee values to occur multiple times instead.</p><p>The modified <strong>V_ℕ</strong> qualifies as an <em>abstract tuple</em> or a building block of a dict, which allows us to look up items in a set by their index.</p><p>The indexing is done by <em>filtering</em>: <strong>V_ℕ(j) = {(i, v_i) ∈ V_ℕ | i = j}</strong>. Unlike tuple indexing, it can be performed <em>regardless</em> of whether the item exists, rather than “throwing a no-such-item error”.</p><p>It returns a set <strong>{(j, v_j)}</strong> with <strong>j</strong>-th key-value pair if it exists, otherwise returns an empty set <strong>{}</strong></p><p><strong><em>Dict</em></strong></p><p>The difference between a dict and an abstract tuple is that the elements are indexed not by <em>counter</em> <strong>i</strong>, but unique key <em>identifiers</em> <strong>k_i</strong>.</p><p>So, additionally, a dict requires a <em>hash function</em> <strong>h: K → ℕ</strong> which <em>maps</em> the key identifier to an index uniquely, also this should always evaluate to true: <strong>∀(k_i, k_j) ∈ K × K: h(k_i) = h(k_j) → k_i = k_j</strong>.</p><p>Assuming such a function exists, now we’re ready to create a dict called <strong>V_K = {(h(k_i), v_i) | k_i ∈ K, v_i ∈ v_1, v_2, …}</strong>, which is the same as <strong>V_ℕ</strong> but with <strong>h</strong> as a <em>perfect</em> built-in hash function.</p><p>Lookup by key <strong>k</strong> is performed similarly: <strong>H_i(k) = {(h(k_i), v_i) ∈ H_i | h(k_i) = h(k)}</strong></p><h4>Dependency Injection on Person-Animal Comparison</h4><p>Let’s go back to the first example where we compare person’s age and a species’ age. Now we can cast:</p><ul><li>person <em>tuple</em> <strong>P_i = (a_i, w_i, h_i)</strong> to a <em>dict</em> <strong>H_i = {(h(“age”), a_i), (h(“weight”), w_i), (h(“height”), h_i)}</strong>, and</li><li>animal <em>tuple</em> <strong>A_j = (z_j, h_j, w_j, a_j)</strong> to another <em>dict</em> <strong>H_j = {(h(“genus”), z_j), (h(“height”), h_j), (h(“weight”), w_j), (h(“age”), a_j))}</strong>.</li></ul><p>Now, looking up the age of human has the same <em>underlying complexity</em> as animal. Below are some interesting analogies:</p><ul><li><code>interface AgeComparable { int age(); }</code> is a dict <strong>H</strong> which contains an age feature.</li><li><code>class Person implements AgeComparable { int age; ...; int age() { return this.age; }; }</code> is a tuple <strong>P</strong> with a defined age <em>endpoint</em> for <strong>H</strong>.</li><li><code>bool compare (AgeComparable either, AgeComparable other) { return either.age() &lt; other.age(); }</code>: <code>either.age()</code> corresponds to the value in <strong>H_i(“age”)</strong>.</li><li>In <code>compare(...)</code>: <strong>H_i(“age”)</strong> cannot be empty, because the type <code>AgeComparable</code> requires each class to implement an <code>age(...)</code> function.</li></ul><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*S4qzpVrJYZIOx6XUcv2kIw.png" /><figcaption>Fig 7: Aggregation of Car By Engine and Wheel</figcaption></figure><h4>How Merging Two Tuples Would Work Using Dicts</h4><p>Likewise, you can use the same operation while <em>merging</em> two different tuples, e.g. <strong>X = (a_i, b_i, c_i) </strong>and <strong>Y = (a_j, d_j) </strong>to <strong>H = {“a”: π(a_i, a_j), “b”: b_i, “c”: c_i, “d”: d_j}</strong> and then to <strong>Z = (a, b, c, d)</strong>.</p><p>Hereby we define a function <strong>π: A × A → A</strong> which selects any of both arguments based on a selecting criteria.</p><p>It corresponds to the custom implementation of a constructor in a class:</p><ul><li><code>class Z implements XInterface, YInterface { int a, b, c, d; Z(X x, Y y) { this.a = x.a; // same as π(x.a, y.a) = x.a ... }; int a() { return this.a; }; ... }</code>,</li></ul><p>given <code>class X implements XInterface {...}</code> and the same for class Y.</p><p>Internally, that happens:</p><ul><li>Cast X to <strong>H_x = {(h(“a”), a_i), (h(“b”), b_i), (h(“c”), c_i)}</strong> and Y likewise to <strong>H_y = {(h(“a”), a_j), (h(“d”), d_j)}</strong></li><li>Define the set of keys for <strong>H_z</strong> as the unified set of the keys of<strong> H_x </strong>and <strong>H_y: K(H_z) = K(H_x) ∪ K(H_y) = {“a”, “b”, “c”} ∪ {“a”, “d”} = {“a”, “b”, “c”, “d”}</strong></li><li>For each key <strong>k</strong> in <strong>K(H_z)</strong>, perform lookup for both <strong>H_x</strong> and <strong>H_y.</strong></li><li>If the result of <strong>H_x(k)</strong> and <strong>H_y(k)</strong> is in conflict, select one of them using <strong>v = π(…, …)</strong>, otherwise exactly one of them should return a non-empty result <strong>v = …</strong></li><li>After initializing <strong>v</strong>, update <strong>H_z = H_z ∪ {(h(k), v)}</strong></li><li>Extract a new tuple <strong>Z</strong> from <strong>H_z </strong>simply by getting the values: <strong>Z = (π(a_i, a_j), b_i, c_i, d_j)</strong></li></ul><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*4XFshy3_gkVoGlFmPSxL3A.png" /><figcaption>Fig 8: Joining Tables Using SQL</figcaption></figure><h4>How Tuple vs. Dict Relationship Is Related to Joining Datasets</h4><p>I discussed previously in one of my articles, how “Logic Is Built On Relations”.</p><p><a href="https://medium.com/thedevproject/logic-is-built-on-relations-371ea2a547aa">Logic Is Built On Relations</a></p><p>It revolves around <em>relations</em> ( = subsets of sets of tuples), simplistically the same as binary information holders.</p><p>Signature corresponds to the list of <em>columns</em> of a dataset, and a structure to a <em>dataset</em> itself.</p><p>The idea behind the signature — structure relationship is roughly the same as tuple — dict relationship:</p><ul><li>Why a <em>structure</em> ( = a class) is defined as a tuple,</li><li>How a <em>signature</em> ( = an interface) serves as a common interface for structures with the same special methods like a set of keys in a dict, and</li><li>How the <em>merging</em> of two structures results as a new structure, similarly to how the merging of X and Y results as a new tuple Z.</li></ul><h4>Conclusion</h4><p>Tuples are the main data structures for storing information in mathematical universe.</p><p>Although tuples are strict, efficient and completely safe to use, these features are also associated with restrictions and inflexibility.</p><p>Dicts are the intermediary data structures used for performing “whichever task a tuple cannot perform”.</p><p>Algebraically, it’s not different than a set of key-value pairs with a built-in hash function, yet it is much more powerful for tasks such as performing lookups, merging tuples, etc.</p><p>Unsurprisingly, this relationship is already known, see common analogies such as class — interface and signature — structure.</p><p>Using mainly tuple — dict analogy, it’s somehow interesting to resurface some best practices for Dependency Injection.</p><h4>References</h4><p>Fig 2: <a
