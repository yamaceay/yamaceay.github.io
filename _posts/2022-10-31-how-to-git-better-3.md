<p>… so you can be a more decent human being in the next projects :-)</p><p>Please make sure you have read my previous articles:</p><p><a href="https://yamaceay.medium.com/how-to-git-better-1-ef996cb86a23">How To Git Better— 1</a></p><p><a href="https://yamaceay.medium.com/how-to-git-better-2-16182a6c0d2e">How To Git Better— 2</a></p><h4>Rebasing ≠ Applying Changes to Branches</h4><p>I hate to admit, but I underestimated rebase a little bit.</p><p>We have previously discussed that branches are similar to processes / workflows, so understanding the branches is key to understanding what others are doing.</p><p>Best practice would be then keeping a branch brief, explainable and to-the-point, as any workflow description would look like.</p><p>But you cannot really create a one huge commit for each branch, that would be counter-productive.</p><p>Instead, you can rewrite the history, after you finalize the updates on a branch.</p><p>That’s why you need to perform interactive rebase on your branch, before opening a pull request.</p><h4>Interactive Rebasing Using Visual Studio Code</h4><p>Interactive rebasing comes in handy, when you want to edit the commit history in a fashionable manner.</p><p>For this, you need to set up VSCode on your computer.</p><p>I created a <a href="https://github.com/yamaceay/git-example">sample project</a> for experimenting. I wrote the code messy on purpose, so that we can clean the commit history. Let’s see an example:</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*YK59OoJfkI2JFD7c04bnLw.png" /></figure><p>Let’s start with interactive rebasing:</p><ol><li>Clone the repository:</li><li>Make sure you have installed Code Path on your Terminal (View -&gt; Command Palette -&gt; Shell command: Install ‘code’ command in P…)</li><li>Make sure you are in the target branch ‘enrich-posts’. If not, use <code>git checkout enrich-posts</code></li><li>Enter <code>git rebase -i HEAD~6</code>` where 6 is the number of commits that you want to affect and <code>-i</code> stands for interactive.</li><li>After configuring the options correctly (see the next sections), click Start Rebase.</li></ol><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*S_GryArr1PMnHGQV8bVMyg.png" /></figure><h4>Commit Edit Message</h4><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*2I6TsV57G5NzunihghLNwQ.png" /></figure><p>Note: In case you selected an option in interactive rebase, so that at least one commit message will be affected, a COMMIT_EDITMSG file will pop up in your side tab. After writing the new commit message, you simply close the tab to apply the commit message.</p><h4>Execution Flags</h4><p><code>--continue</code>: Apply the new changes in the current issue and execute the rebase again.</p><p><code>--skip</code>: Ignore the current issue and execute the rebase again.</p><p><code>--abort</code>: Abort the rebase and return back to the original situation before the rebase.</p><p><code>--quit</code>: Quit the rebase at the current situation during the rebase.</p><h4>Order of Commits</h4><p>Did you know that you can change the order of commits by dragging the commits up / down?</p><p>As cool as it may sound, it really comes handy in some use cases.</p><p>For example, if you want to squash two similar commits which are distant from each other, you can simply drag the commit on the other one and then squash them.</p><p>It is — in my opinion — a bad habit to change the order of commits, instead of changing the commit messages, but it is up to you.</p><h4>Types of Operations</h4><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*c9cxJAXlohvzRXugDGgFoQ.png" /></figure><p><em>pick</em>: Include the commit in the history, default option with no effect.</p><p><em>drop</em>: Exclude the commit from the history, same as deleting the corresponding commit message from the commit history.</p><p><em>reword</em>: Rewrite the commit message without changing the content.</p><p><em>edit</em>: Pause the rebase, edit the code, stage the changes, commit with a descriptive message, then continue the rebase.</p><p><em>squash</em>: Squash the selected and previous commit into a new commit and use the both messages in the new commit message (not allowed if it is the last commit).</p><p><em>fixup</em>: Squash the selected and previous commit into a new commit, but only include the message of the previous one in the new commit message (not allowed if it is the last commit).</p><h4>Other Commands Used With Rebase</h4><p><code>git commit --amend</code>: Equivalent to committing the new changes as a commit and then performing interactive rebase on the last two commits where the commit on the top is marked as <code>fixup</code>.</p><p><code>git push --force-with-lease</code>: It is used to forcefully replace the commit history of remote branches with the commit history of local branches.</p><p>I wouldn’t recommend using <code>git push --force</code> instead, since it can cause you to delete someone else’s recent commits, while <code>git push --force-with-lease</code> doesn’t allow you that.</p><p>That’s why <code>git push --force-with-lease</code> is almost always the better option.</p><p>Let’s perform an exemplary rebase operation!</p><h4>An Example of Successful Rebasing</h4><p>First things first, I want to see how the changes look like. Let’s look how different the second commit (green) looks like from the third commit (red), which includes more than adding marshal functions.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*6qbWkO_juxXOVaSvnCRZtA.png" /></figure><p>In this case, this is what I want to do:</p><ul><li><em>Fixup</em> the first commit into the second commit, because they do exactly the opposite.</li><li><em>Split</em> the second commit into two commits: second one includes implementing custom marshal functions, and the first one on the top should include everything else. We can do this by pausing on this commit, resetting all changes and committing all changes in two parts.</li><li><em>Squash</em> / <em>Fixup</em> the third commit onto the fourth commit, because it is not necessarily a good idea to write refactoring commits when cleaning the history.</li><li><em>Pick</em> the fourth commit, because it is a necessary and a useful commit.</li><li><em>Squash</em> the fifth onto sixth commit, because we don’t want to know about which conflicts have happened.</li></ul><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*04klhPmtxIwv65YfmEnd7w.png" /></figure><p>At the end, it looks more understandable. Thanks Git!</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*IHnBswMsyuz3i8du0NGHyw.png" /></figure><p>I hope you enjoyed my articles!</p><p>The primary reason I created these articles was to note down things about Git that I learned during my job, as well as my own experiences.
