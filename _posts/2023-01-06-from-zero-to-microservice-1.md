<h4>How to Design API, Server &amp; Client With Ease?</h4><p>Previous article:</p><p><a href="https://yamaceay.medium.com/microservices-101-d6395c153890">Microservices 101</a></p><p>Next article:</p><p><a href="https://yamaceay.medium.com/from-zero-to-microservice-2-89fdeb96b823">From Zero to Microservice [2]</a></p><h4>What is gRPC (Again)?</h4><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*1mFXScMgeWJubykgQRmL4w.png" /><figcaption>Fig 1: A Cloud-Native application using gRPC for communication, Source: <a href="https://learn.microsoft.com/de-de/dotnet/architecture/cloud-native/grpc">https://learn.microsoft.com/de-de/dotnet/architecture/cloud-native/grpc</a></figcaption></figure><blockquote>gRPC is a modern open source high performance Remote Procedure Call (RPC) framework that can run in any environment. [1]</blockquote><p>It lets you:</p><p><em>define</em> the service interface and the structure of the payload messages using Protobuf (Protocol Buffers) in a Protobuf file named e.g. <code>&lt;service&gt;.proto</code>, then</p><p><em>generate</em> the server and client stubs automatically using <code>&lt;service&gt;.proto</code> in a variety of languages and platforms, but also</p><p><em>integrate</em> bi-directional streaming and authentication features of HTTP/2</p><h4>Planning</h4><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*8HZQavg7s1yCPYutRMD9lw.png" /><figcaption>Fig 2: A DB consisting of key-value pairs, Source: <a href="https://www.scylladb.com/glossary/key-value-database/">https://www.scylladb.com/glossary/key-value-database/</a></figcaption></figure><p>Let’s start with the following user story:</p><p><em>As an end user, I want to perform read/write operations on person data.</em></p><p>So we want to design a microservice which looks up person by a selected identifier and/or updates person data.</p><p>I choose Go as the programming language due to its simplicity and high speed.</p><p>Instead of creating HTTP server / client from scratch, I prefer to use gRPC for code generation.</p><h4>Setup</h4><p><em>Setup folder structure (I named it </em><code><em>person</em></code><em>):</em></p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*aQYvISrHHuvpOM1Tt-y4Iw.png" /><figcaption>Fig 3: Folder structure</figcaption></figure><p><em>Initialize Git</em>: <code>git init</code></p><p><em>Create a Go package</em>: <code>go mod init github.com/&lt;your-grpc&gt;</code></p><p><em>Install dependencies</em>:</p><ul><li><code>go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@v1.2</code></li><li><code>go install google.golang.org/protobuf/cmd/protoc-gen-go@v1.28</code></li></ul><p><em>Save installed programs into PATH</em>: <code>export PATH=&quot;$PATH:$(go env GOPATH)/bin&quot;</code></p><h4>API Design</h4><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*coJfRLW_0bmcin-ZAkFSkw.png" /><figcaption>Fig 4: Protocol Buffers used for API design, Source: <a href="https://www.xenonstack.com/insights/google-protocol-buffer/">https://www.xenonstack.com/insights/google-protocol-buffer/</a></figcaption></figure><p>Rephrasing User Story: The server / client should be able to perform get / set operations on a DB consisting of personal data.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*Yt378OkaQQrypMLCcuogDA.png" /><figcaption>Fig 5: Proto file header</figcaption></figure><p>I set the name of package: <code>person</code> (see 7, later in the code generation: a Go package <code>person</code> will be created). The path of Go package should be specified as: <code>&lt;parent&gt;/person</code> (see 3).</p><p>Using the documentation [2], I defined a brand new service “PersonQuery” as follows.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*43ex1NWNpUMQcYEZxAjF0A.png" /><figcaption>Fig 6: A service definition</figcaption></figure><p>Service definition is what a client sees from the outside. It specifies all methods which can be called remotely using stubs.</p><p>Each remote procedure contains exactly one input and one output message. If no input / output is specified, an empty message can be used instead (see 24).</p><p>An input / output message can also be a stream message, which means it blocks the procedure and reads / writes data until termination condition reached (see 15, 18 and 21).</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*DJU73pHvUbLa6uQwzXaeKw.png" /><figcaption>Fig 7: A message with a single field</figcaption></figure><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*zoWJoKQF3LaMZelOdywDew.png" /><figcaption>Fig 8: A message with simple fields</figcaption></figure><p>A message specifies the payload message which can be used as input / output. Message fields have a type (e.g. string, float) and the order inside message, starting with 1.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*XaVnThzzSQr9rhBFW_z_9w.png" /><figcaption>Fig 9: An enum defined in message</figcaption></figure><p>Enum is defined similarly as a message type, but its order is also equal to its values. Zero is the default value of an enum (see 42).</p><p>If a field is removed from a message in a new version of the service, the reserved field numbers (see 50) should never be reused.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*X91_tEvq6bPhZP1EKFOQBg.png" /><figcaption>Fig 10: An inner message extending its parent message by new fields</figcaption></figure><p>Similarly how aggregation works [3], the messages can extend a message type by including its payload (see 60).</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*l6EcvjdsK3Vvm041fO13RA.png" /><figcaption>Fig 11: Optional fields</figcaption></figure><p>A message can contain also optional fields, which are set to their default value, if not set.</p><p>Type-specific default values are: zero, empty string, false, or a null pointer otherwise. The exact implementation of null pointer depends on the language (NULL in C++, None in Python, nil in Golang, …).</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*-dQhaDJdqp0HRD6D1XCiig.png" /><figcaption>Fig 12: More complex fields</figcaption></figure><p>Union concept is not widely accepted in all languages: You have to use exactly one of the fields in a message. If that’s the case (see 84), you can use <code>oneof &lt;union&gt; { ... }</code> to guarantee that exactly one element inside a message is used at once.</p><p>If the requirements of a fields are not fully understood, or you have to iterate over its fields, you can use <code>map&lt;&lt;key_type&gt;, &lt;value_type&gt;&gt;</code> as a new field type. Similarly, map concept is not implemented across all languages, too.</p><p>Using <code>repeated</code> at the beginning of a simple field, an 1-dimensional array of same type can be defined.</p><h4>Code Generation</h4><p>Enter the following command in terminal to generate the client and server stub:</p><p><code>protoc --go_out=. --go_opt=paths=source_relative --go-grpc_out=. --go-grpc_opt=paths=source_relative &lt;your-stub&gt;/&lt;your-stub&gt;.proto</code></p><p>Here are the instant results:</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*jcfv0QlejDKgQAeqdObfag.png" /><figcaption>Fig 13: service PersonQuery -&gt; interface PersonQueryClient</figcaption></figure><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*69OR1wn-Ne3es1aEjs40Pw.png" /><figcaption>Fig 14: service PersonQuery -&gt; interface PersonQueryServer</figcaption></figure><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*EQ6_7_2ywZcXqCNufVxFjg.png" /><figcaption>Fig 15: message Person -&gt; struct Person (with all getter/setter methods)</figcaption></figure><h4>Implement the service</h4><p>The API is successfully created, it’s time to implement the server and the client.</p><p><code>server/main.go</code>:</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*77sUwHitRt0F0oJncBMufQ.png" /><figcaption>Fig 16: Server implementation</figcaption></figure><p><em>Line 23</em>: Server is defined as a data structure with server payload and optional fields you wish to use.</p><p><em>Lines 28, 44</em>: Server struct implements methods GetPerson and SetPerson. Since other methods won’t be used, they are implemented as empty functions.</p><p><em>Lines 29, 46</em>: Message type <code>Person</code> has built-in getter methods for each field <code>x</code>, named as <code>GetX</code>.</p><p><em>Line 45</em>: Empty message type is initialized.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*ks1gh689QJSKvWn89dMpag.png" /><figcaption>Fig 17: Server main function</figcaption></figure><p><em>Line 79</em>: Initialize listener which will accept client connections on specified TCP port</p><p><em>Lines 89–90</em>: Initialize a new gRPC server, which copies the attributes and methods of <code>PersonQueryServerStruct</code></p><p><em>Line 93</em>: Accept client connections and perform operations</p><h4>Implement the client</h4><p>Now that gRPC server works as expected, we can define the front-end of the application.</p><p>It translates the requests made by end user to valid Remote Procedure Calls on the server, as follows:</p><p><code>client/main.go</code>:</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*GC3ueALbae4PkowBL6WRUQ.png" /><figcaption>Fig 18: Client main function</figcaption></figure><p><em>Lines 34–35</em>: Connection to the server is established with transport credentials</p><p><em>Line 51</em>: Command execution takes place (more in the next image)</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1400/1*NOhje5XLsIeQmLJSymDOwA.png" /><figcaption>Fig 19: Client-side command execution</figcaption></figure><p><em>Line 59</em>: Since json cannot deal with more complex data structures, protojson has to be used instead.</p><p><em>Lines 62, 69</em>: Here are two examples of Remote Procedure Calls. Methods are called remotely from PersonQueryClient and the call is forwarded to PersonQueryServer.</p><h4>Build &amp; Run the Application</h4><p>Open a new terminal for server</p><p><em>Build server</em>: <code>go build -o &lt;your-server&gt; ./server</code></p><p><em>Run server</em>: <code>go run ./server &lt;args&gt;</code></p><p>Then, open a new terminal for client</p><p><em>Run client</em>: <code>go run client/main.go &lt;args&gt;</code></p><h4>To be Continued …</h4><p>Well, the core functionality is done.</p><p>In the following article, I <em>dockerize</em> the application and <em>deploy</em> it to a local Kubernetes cluster.
